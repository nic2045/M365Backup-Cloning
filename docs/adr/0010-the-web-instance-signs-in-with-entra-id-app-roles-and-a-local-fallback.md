# 0010. The web instance signs in with Entra ID app roles and a local fallback

Status: Accepted (2026-11-07, issue #60). The role of the local account (point 4) is superseded by ADR 0016: Reader only. Fills in "roles and audit" of ADR 0002 for the web API and interface.

## Context
The API (`web/api`) and the interface (`web/ui`) of one toolkit instance were open to anyone who could reach them. They only read today, but the data shows the structure of both tenants, and the write routes of #14 (apply, reset) will need to know who acts and what they may do. The operator already runs the toolkit with an app registration in their own Entra ID. Some instances run on a single admin machine where Entra ID sign-in may not be possible (new tenant, broken federation, offline test).

## Decision
1. **Entra ID with OpenID Connect.** The interface signs in with the authorization code flow with PKCE (S256), `state` and `nonce`. It checks the ID token (signature with the keys of the tenant's OIDC metadata, audience = its client ID, issuer and `tid` of the configured tenant, expiry, nonce). The access token for the API stays in the server-side session and is sent only in the `Authorization` header; it is never written into a page, a script or a log. A registration of the platform "Mobile and desktop applications" with a `http://localhost` redirect needs no client secret; a hosted instance with the platform "Web" also needs a client secret or certificate, taken from the environment or a secret store, never from the repository.
2. **The API checks every request itself.** Every route needs a bearer token. Entra ID tokens: RS256 only; signature with the tenant's JWKS (cached), audience (`M365CLONING_AUTH_AUDIENCE`), issuer `https://login.microsoftonline.com/<tenant>/v2.0` (the app registration uses `accessTokenAcceptedVersion = 2`), `tid`, `exp`/`iat` required, 60 seconds leeway. Library: PyJWT with `cryptography`, pinned and hash-locked. Without a token or with an invalid one the answer is **401**, without the role **403**, both with the `Error` schema; nothing configured means 401 for everything (fail closed).
3. **App roles, not groups in the token.** Roles come from the `roles` claim: `Reader`, `Applier`, `Resetter`. `Applier` and `Resetter` include `Reader`; `Resetter` does not include `Applier`. People get roles through groups assigned to the app roles in the enterprise application (role assignments go through groups, CLAUDE.md). Read routes need `Reader`; the write routes of #14 will need `Applier` or `Resetter`.
4. **Local account as fallback.** Off by default. One account, configured by environment variables or a secret store: user name, password hash, role (default `Reader`). It is offered and accepted only from the loopback address (`127.0.0.1`, `::1`) and only without proxy headers (`Forwarded`, `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Host`), so it never works through a reverse proxy. The hash is scrypt from the Python standard library (`hashlib.scrypt`, n = 2^15, r = 8, p = 1, 16-byte salt, parameters stored in the hash): memory-hard and no extra dependency. Comparison in constant time; an unknown user name runs the same hash. Five failed attempts lock the form for five minutes. There is no self-registration.
5. **Local token for the API.** For a local session the interface signs a token for each call to the API (HS256, issuer `m365cloning-local`, audience `m365cloning-api`, 60 seconds, at most 15 minutes accepted) with a secret both processes share (`M365CLONING_LOCAL_TOKEN_SECRET`, at least 32 bytes). The API accepts it only from the loopback address without proxy headers. Entra ID tokens and local tokens are told apart by the issuer and each accepts exactly one algorithm, so neither can pass as the other.
6. **Sessions.** The browser holds only a random session id in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` on https (or when `M365_UI_COOKIE_SECURE` is set). Sessions live in the memory of the interface process for at most eight hours and never longer than the access token; a restart signs everyone out. Every session has a CSRF token: the logout form uses it, and pages send it as `X-CSRF-Token` with HTMX requests for the write actions of #14. When the API answers 401 the session ends and the browser goes to the sign-in page.
7. **Mock without sign-in.** Only when the interface shows the mock answers and no sign-in is configured it opens for an "Example user", so it can be tried without a tenant. With a real API it requires sign-in.
8. **Audit.** The audit line gets an optional `Actor`: the signed-in person who started an action in the web interface. `User` stays the account that ran the script. Adding an optional field keeps `schemaVersion`.

## Consequences
- Tests never call Entra ID: the key provider of the API and the OIDC provider of the interface are injectable; tests make their own RSA keys and tokens.
- The owner registers the app, defines the app roles and assigns groups (validation/README.md, part "Web sign-in"). Claude cannot check this against a real tenant.
- Sessions in memory fit one process per instance (ADR 0002). Several worker processes would need a shared session store; that is a new decision.
- No refresh token is kept: when the access token expires (usually after about an hour) the person signs in again.
